Ollama: guia completo

Instale, gerencie e integre modelos locais. Aprenda CLI, API, multimodalidade, embeddings, ferramentas e customização com Modelfile.

1. O que é o Ollama

O Ollama baixa e executa modelos de IA por meio de um servidor local. O servidor mantém modelos no armazenamento configurado e oferece CLI, API HTTP e compatibilidade parcial com APIs conhecidas. Open WebUI, n8n, Jupyter, LiteLLM e outros clientes podem usar o mesmo servidor.

Ollama é o runtime e gerenciador do modelo. Não é, sozinho, uma interface completa de chat, banco vetorial, orquestrador de fluxos ou processo de treinamento de pesos. O laboratório combina serviços para esses usos.

Privacidade: chamadas ao servidor local são processadas nesse ambiente. Isso não se aplica automaticamente a integrações externas, modelos em nuvem, plugins ou ferramentas que acessem a internet. Confira para onde cada aplicação envia os dados.

2. Ollama neste laboratório

O serviço Compose chama-se ollama e mantém modelos no volume persistente ollama_storage. A API local não exige autenticação e é publicada somente em 127.0.0.1:11434 no host, não diretamente para toda a rede local.

Onde está o clienteEndereçoExemplos
Windows ou Ubuntu no hosthttp://localhost:11434PowerShell, navegador ou aplicativo no host.
Outro container Composehttp://ollama:11434LiteLLM, n8n, Open WebUI e serviços na rede Docker.
JupyterLab do laboratóriohttp://ollama:11434Código executado no container Jupyter.

Para usar a CLI sem instalação separada, abra o terminal na pasta do projeto (Ubuntu no WSL no Windows) e execute docker compose exec ollama .... Os exemplos assumem o diretório com docker-compose.yml.

Verificar o serviço
docker compose ps ollama docker compose exec ollama ollama --version docker compose exec ollama ollama list

Modelos iniciais: o laboratório baixa llama3.2:3b para geração e nomic-embed-text para embeddings. Outros precisam ser baixados. Confira tags e licenças no catálogo oficial.

3. Modelos, quantização e hardware

3B, 8B e 70B indicam aproximadamente bilhões de parâmetros; não representam diretamente a memória necessária. Execução também depende da quantização, contexto, imagens, lote, arquitetura e backend.

  • Tamanho: modelos maiores podem ter mais capacidade em algumas tarefas, com maior custo de memória e computação.
  • Quantização: reduz a precisão dos pesos para economizar espaço e memória, com possível impacto na qualidade. Tags como Q4_K_M indicam variantes quantizadas.
  • GPU e CPU: pesos que cabem na VRAM podem usar GPU compatível. Também é possível usar CPU ou combinar backends, com velocidades distintas.
  • Contexto: tokens considerados na solicitação. Aumentá-lo tende a consumir mais memória; o limite anunciado não garante execução eficiente nesse hardware.

Comece pelo 3B incluído e compare tamanhos maiores na máquina disponível. Evite tratar estimativas de VRAM como garantia. Use ollama ps para conferir contexto e divisão da carga entre CPU e GPU.

4. Baixar, listar, inspecionar e remover modelos

Listar e baixar

Terminal do projeto · WSL ou Ubuntu
# Modelos armazenados localmente docker compose exec ollama ollama list # Baixar modelos de texto e embeddings docker compose exec ollama ollama pull llama3.2:3b docker compose exec ollama ollama pull nomic-embed-text # Exemplo de outro modelo (confirme tag e tamanho no catálogo) docker compose exec ollama ollama pull qwen3:4b

Downloads podem ocupar gigabytes e precisam de internet. Os arquivos ficam no volume persistente.

Executar, inspecionar e remover

Comandos de gerenciamento
# Conversa no terminal; encerre com /bye docker compose exec -it ollama ollama run llama3.2:3b # Metadados e receita gravada docker compose exec ollama ollama show llama3.2:3b docker compose exec ollama ollama show --modelfile llama3.2:3b # Modelos carregados na memória docker compose exec ollama ollama ps # Descarregar da memória, mas preservar arquivos docker compose exec ollama ollama stop llama3.2:3b # Apagar modelo do armazenamento docker compose exec ollama ollama rm qwen3:4b

ollama list mostra o que está armazenado; ollama ps, o que está carregado. stop libera memória; rm apaga arquivos e pode exigir novo download.

5. CLI, entrada interativa e integrações

A CLI recebe uma pergunta ou abre um chat interativo. Executá-la no container mantém a versão consistente com o serviço:

Pergunta direta e chat
docker compose exec ollama ollama run llama3.2:3b "Explique embeddings em três frases." docker compose exec -it ollama ollama run llama3.2:3b # No chat: /bye encerra. Para texto multilinha, delimite com três aspas.

Em execução independente no host, ollama serve inicia o servidor; no laboratório o Compose já inicia esse processo. Em versões compatíveis, ollama launch auxilia a configurar integrações; ollama signin e ollama signout gerenciam conta. Integrações e modelos em nuvem são opcionais e não fazem parte do perfil local padrão.

6. Modelfile: conceito e limites

Um Modelfile é uma receita declarativa para criar uma variante de modelo. Define a base, comportamento, parâmetros de inferência, template e mensagens de exemplo. A variante pode ter nome próprio e ser reutilizada por alunos, aplicações e fluxos.

Modelfile não treina nem altera os pesos da base. Ele personaliza a inferência e o prompt. Fine-tuning/LoRA são processos distintos, que produzem artefatos próprios. Importar pesos preparados também não equivale a treinamento.

Instruções não diferenciam maiúsculas de minúsculas. FROM é obrigatória; mantenha-a no início para facilitar leitura. Salve com o nome exato Modelfile, sem extensão extra.

7. Referência de todas as instruções

InstruçãoFinalidadeExemplo
FROMObrigatória. Base por tag, diretório Safetensors compatível ou arquivo GGUF.FROM llama3.2:3b
PARAMETEROpções de inferência, contexto, amostragem e limite de geração. Pode repetir.PARAMETER temperature 0.2
SYSTEMMensagem de sistema, se o template da base usar o campo.SYSTEM """Responda em português."""
TEMPLATESerialização de mensagens em tokens/texto; depende do modelo.veja o exemplo completo abaixo
MESSAGEMensagens de exemplo com papel system, user ou assistant.MESSAGE user Olá
LICENSERegistra licença associada; não substitui a checagem da licença da base.LICENSE """Texto da licença"""
REQUIRESVersão mínima do Ollama exigida.REQUIRES 0.14.0
CAPABILITYAdiciona capacidade a modelos GGUF/MLX quando aplicável; não torna pesos incompatíveis capazes de uma tarefa.CAPABILITY decision apenas em pesos compatíveis, treinados para System One.

Cuidado com TEMPLATE: não copie template de outra família sem conhecer tokens especiais. Comece com o template herdado, inspecionado por ollama show --modelfile, e altere sistema e parâmetros. Um template incompatível pode quebrar conversas e tool calling.

Template: variáveis e sintaxe Go

O campo TEMPLATE é um template Go e representa como a conversa vira entrada do modelo. As variáveis documentadas mais comuns são {{ .System }} (mensagem de sistema), {{ .Prompt }} (prompt do usuário) e {{ .Response }} (ponto onde começa a resposta gerada; o texto posterior é omitido na geração). Condições como {{ if .System }} e {{ end }} permitem incluir partes apenas quando há conteúdo.

Exemplo ilustrativo de um formato ChatML. Os tokens são específicos desse formato e este bloco não deve substituir o template do llama3.2; consulte primeiro o template exato da sua base. Tokens finais e sequências stop também precisam combinar com o modelo.

Exemplo didático · adapte à arquitetura correta
TEMPLATE """{{ if .System }}<|im_start|>system {{ .System }}<|im_end|> {{ end }}{{ if .Prompt }}<|im_start|>user {{ .Prompt }}<|im_end|> {{ end }}<|im_start|>assistant {{ .Response }}<|im_end|>"""

SYSTEM define a mensagem de sistema usada pelo template. MESSAGE system ... é uma forma alternativa; mensagens MESSAGE user e MESSAGE assistant criam exemplos de contexto e podem ser repetidas em pares. Comentários começam com #. Blocos longos podem usar aspas triplas.

8. Parâmetros do Modelfile

Parâmetros reconhecidos na referência atual. Defaults podem variar por modelo e versão. Faça alterações graduais e compare um conjunto fixo de solicitações.

ParâmetroO que controlaTipo / exemplo
num_ctxJanela de contexto; aumentar tende a exigir mais memória.inteiro · num_ctx 4096
repeat_last_nTokens anteriores considerados para repetição; 0 desativa, -1 usa o contexto.inteiro · repeat_last_n 64
repeat_penaltyForça da penalização; valores maiores penalizam mais.decimal · repeat_penalty 1.1
temperatureVariação da amostragem; menor tende a ser mais previsível.decimal · temperature 0.3
seedSemente para maior reprodutibilidade, sem garantir igualdade em todo backend.inteiro · seed 42
stopSequência de parada; repita para declarar várias.texto · stop "###"
num_predictMáximo de tokens de saída; -1 não configura limite.inteiro · num_predict 512
draft_num_predictTokens especulativos quando há modelo draft; sem draft não tem efeito útil.inteiro · draft_num_predict 4
top_kLimita candidatos aos K tokens mais prováveis.inteiro · top_k 40
top_pAmostragem pela massa acumulada de probabilidade.decimal · top_p 0.9
min_pFiltra candidatos por probabilidade relativa ao token mais provável.decimal · min_p 0.05

Opções também podem ser enviadas por requisição em options. Preserve tokens stop exigidos pela base quando modificar templates.

9. Exemplo completo: tutor de estudos

O exemplo parte do modelo 3B incluído, define o comportamento, configura parâmetros moderados e mostra uma resposta-modelo. Ajuste após comparar resultados; as opções não são universais.

Passo 1 — criar o arquivo

Na pasta do projeto, crie um arquivo chamado Modelfile com este conteúdo:

Arquivo Modelfile
FROM llama3.2:3b SYSTEM """Você é um tutor de inteligência artificial. Responda em português do Brasil, explique termos técnicos com clareza e organize respostas longas em etapas. Quando não souber, diga isso. Não invente fontes, números nem resultados de execução.""" PARAMETER temperature 0.3 PARAMETER num_ctx 4096 PARAMETER num_predict 512 PARAMETER top_p 0.9 PARAMETER repeat_penalty 1.1 MESSAGE user "O que é um embedding?" MESSAGE assistant "É uma representação numérica de um conteúdo, como texto. Ela permite comparar significados e encontrar conteúdos relacionados."

Passo 2 — copiar ao container e criar

No WSL/Linux, na pasta do projeto, obtenha o ID do container gerenciado pelo Compose, copie o Modelfile e crie a variante:

WSL ou Linux · Bash
OLLAMA_CONTAINER=$(docker compose ps -q ollama) docker cp ./Modelfile "$OLLAMA_CONTAINER:/tmp/Modelfile" docker compose exec ollama ollama create tutor-ia:local -f /tmp/Modelfile

Se o primeiro comando não retornar um ID, inicie docker compose up -d ollama e repita. O resultado persiste no volume do Ollama.

Passo 3 — testar e integrar

Testar o modelo criado
docker compose exec ollama ollama list docker compose exec ollama ollama run tutor-ia:local "Explique RAG e proponha um exercício." docker compose exec ollama ollama show --modelfile tutor-ia:local

Selecione tutor-ia:local em um cliente Ollama. Para usar via LiteLLM, registre a variante em config/litellm/config.yaml; criá-la no Ollama não adiciona entrada ao gateway. Edite o Modelfile e execute novamente ollama create para atualizar. Use ollama rm tutor-ia:local para remover apenas a variante.

10. Importar bases GGUF ou Safetensors

FROM aceita uma tag, um diretório Safetensors de arquitetura compatível ou arquivo GGUF. Caminhos relativos são resolvidos a partir do Modelfile. GGUF fragmentado precisa preservar nomes e incluir todos os fragmentos.

Exemplos dentro do Modelfile
# Modelo já disponível no Ollama FROM llama3.2:3b # Arquivo GGUF ao lado do Modelfile FROM ./modelo-quantizado.gguf # GGUF fragmentado FROM ./modelo-quantizado-*.gguf # Diretório Safetensors compatível FROM ./modelo-safetensors/

Arquivos do host precisam estar visíveis no container durante ollama create; copie-os ou monte-os no container e use esse caminho. Ollama não quantiza GGUF automaticamente durante importação. Prepare os pesos e confira a licença antes de compartilhar.

11. API REST local

A API nativa usa HTTP na porta 11434. Use localhost no host e ollama dentro da rede Compose. O serviço precisa estar ativo e o modelo baixado.

Geração de texto: /api/generate

Recebe um prompt único. stream: false retorna um JSON completo; no modo REST o streaming é ativado por padrão.

WSL/Linux · cURL
curl http://localhost:11434/api/generate \ -H "Content-Type: application/json" \ -d '{ "model": "llama3.2:3b", "prompt": "Explique latência de rede em uma frase.", "stream": false }'

Chat com histórico: /api/chat

Mensagens e opções
curl http://localhost:11434/api/chat \ -H "Content-Type: application/json" \ -d '{ "model": "llama3.2:3b", "messages": [ {"role": "system", "content": "Responda em português e seja objetivo."}, {"role": "user", "content": "O que é RAG?"} ], "stream": false, "options": {"temperature": 0.3, "num_ctx": 4096} }'

Para continuar a conversa, a aplicação cliente mantém e reenvia mensagens anteriores. No PowerShell, Invoke-RestMethod evita diferenças do alias curl:

PowerShell · gerar texto
$body = @{ model = 'llama3.2:3b' prompt = 'Explique embeddings em uma frase.' stream = $false } | ConvertTo-Json Invoke-RestMethod -Uri 'http://localhost:11434/api/generate' -Method Post -ContentType 'application/json' -Body $body

12. Capacidades do Ollama

Recursos variam conforme modelo e versão. Consulte ollama show ou /api/show. O suporte do endpoint a um campo não garante que todo modelo consiga usá-lo.

Streaming

Streaming entrega partes enquanto o modelo gera, reduzindo a espera percebida. É padrão no REST; envie "stream": false para receber resposta completa. Clientes devem acumular fragmentos para montar a resposta.

JSON e saídas estruturadas

Envie format: "json" ou um JSON Schema em format. Isso restringe a estrutura, mas não garante conteúdo verdadeiro. Valide a resposta no cliente.

Exemplo com JSON Schema
curl http://localhost:11434/api/chat \ -H "Content-Type: application/json" \ -d '{ "model": "llama3.2:3b", "messages": [{"role": "user", "content": "Classifique: O servidor não inicia. Retorne categoria e urgência."}], "format": { "type": "object", "properties": { "categoria": {"type": "string"}, "urgencia": {"type": "string"} }, "required": ["categoria", "urgencia"] }, "stream": false }'

Visão e imagens

Modelos de visão aceitam texto e imagem. A API REST espera imagens Base64 em images; SDKs também podem aceitar caminho, bytes ou URL. O llama3.2:3b do laboratório é modelo de texto: baixe um modelo multimodal compatível para essa tarefa.

Para experimentar, instale gemma3:4b, um modelo multimodal de visão; a variante padrão quantizada ocupa cerca de 3,4 GB no disco e requer Ollama 0.6 ou posterior. Confira os termos de uso e o espaço disponível antes do download.

Terminal do projeto · baixar a base de visão
docker compose exec ollama ollama pull gemma3:4b
Notebook Jupyter · enviar uma imagem
from ollama import chat caminho_imagem = "/caminho/visivel/no/notebook.png" resposta = chat( model="gemma3:4b", messages=[{ "role": "user", "content": "Descreva o que aparece nesta imagem.", "images": [caminho_imagem], }], ) print(resposta.message.content)

Embeddings e RAG

Embeddings transformam textos em vetores para busca semântica e RAG. O projeto inclui nomic-embed-text. Use o mesmo modelo e dimensão para indexar e consultar. Divida documentos em blocos antes de embeddar e armazene os vetores no Qdrant ou banco compatível.

Embeddings em lote
curl http://localhost:11434/api/embed \ -H "Content-Type: application/json" \ -d '{ "model": "nomic-embed-text", "input": ["Primeiro texto para indexação.", "Segundo texto relacionado."], "truncate": false }'

Tool calling (chamada de ferramentas)

Exercício no notebook: instale o modelo com docker compose exec ollama ollama pull qwen3:4b. O SDK converte a função Python em definição de ferramenta; o aluno executa a função localmente e devolve o resultado para o modelo compor a resposta final.

Tool calling com SDK Python · função fictícia local
from ollama import chat def consultar_temperatura(cidade: str) -> str: """Retorna uma temperatura de exemplo para uma cidade.""" tabela = {"Brasília": "25 °C", "São Paulo": "22 °C"} return tabela.get(cidade, "Sem dado de exemplo") mensagens = [{"role": "user", "content": "Qual a temperatura em Brasília?"}] resposta = chat(model="qwen3:4b", messages=mensagens, tools=[consultar_temperatura]) mensagens.append(resposta.message) if resposta.message.tool_calls: chamada = resposta.message.tool_calls[0] resultado = consultar_temperatura(**chamada.function.arguments) mensagens.append({ "role": "tool", "tool_name": chamada.function.name, "content": str(resultado), }) final = chat(model="qwen3:4b", messages=mensagens, tools=[consultar_temperatura]) print(final.message.content) else: print(resposta.message.content)

Thinking / modelos de raciocínio

Alguns modelos separam um campo thinking e aceitam think. Valores variam por modelo: consulte /api/show. A aplicação deve decidir o que exibir e não expor rastros internos automaticamente.

Modelos de decisão

Versões recentes também oferecem modelos especializados em classificação, escolha entre categorias e avaliação por níveis. O recurso System One requer Ollama v0.35 ou superior e modelos treinados para essa tarefa; ele não é uma capacidade genérica de qualquer LLM.

Exemplo opcional · classificar chamado com Nimble
docker compose exec ollama ollama pull nimble docker compose exec ollama ollama run nimble --ask "Qual equipe deve cuidar deste chamado?" --choice suporte="Suporte técnico" --choice financeiro="Financeiro" < chamado.txt

Cloud, busca na web e integrações externas

Ollama Cloud e a API de busca na web são recursos online opcionais, distintos da inferência local. Modelos Cloud e busca exigem autenticação/credencial e enviam solicitações ao serviço hospedado. A busca web usa a API https://ollama.com/api/web_search; mantenha a chave fora do notebook compartilhado, do frontend e do Git.

Busca web opcional · WSL/Linux · requer API key
export OLLAMA_API_KEY="sua-chave" curl https://ollama.com/api/web_search \ -H "Authorization: Bearer $OLLAMA_API_KEY" \ -H "Content-Type: application/json" \ -d '{"query":"documentação do Ollama","max_results":5}'

Outros recursos incluem ollama launch para integrações suportadas e compatibilidade parcial com clientes OpenAI e Anthropic. A disponibilidade depende da versão, do aplicativo e da configuração. Eles não são ativados pelo Compose local padrão.

13. Python, Jupyter e compatibilidade

SDK Ollama no Jupyter

JupyterLab está na rede Docker; dentro do notebook, use http://ollama:11434. Se o pacote não estiver instalado no kernel, instale-o:

Notebook · Python
%pip install ollama from ollama import chat resposta = chat( model="llama3.2:3b", messages=[{"role": "user", "content": "Explique o que é um modelo local."}], stream=False, ) print(resposta.message.content)

Em Python executado no host, use http://localhost:11434. Em containers Compose, o endereço DNS é ollama.

Cliente compatível com OpenAI

Ollama oferece um subconjunto de compatibilidade em /v1; nem todos os recursos ou formatos são equivalentes. A chave abaixo é exigida pelo cliente, mas ignorada pelo servidor local.

Notebook · cliente OpenAI para Ollama local
%pip install openai from openai import OpenAI client = OpenAI( base_url="http://ollama:11434/v1/", api_key="ollama", ) resposta = client.chat.completions.create( model="llama3.2:3b", messages=[{"role": "user", "content": "Defina inferência local em uma frase."}], ) print(resposta.choices[0].message.content)

Para clientes internos, o laboratório também oferece LiteLLM em http://litellm:4000, com gateway e observabilidade conforme a configuração do projeto.

14. Desempenho, configuração e solução de problemas

Diagnóstico

Terminal do projeto
docker compose ps ollama docker compose logs --tail=100 ollama docker compose exec ollama ollama ps docker stats

Em GPU NVIDIA, confira também nvidia-smi no host Linux/WSL e se o runtime disponibiliza a GPU aos containers. Sem GPU, Ollama pode executar em CPU, com desempenho diferente.

Configurações do Compose do laboratório

O serviço usa OLLAMA_KEEP_ALIVE=10m, OLLAMA_MAX_LOADED_MODELS=1, OLLAMA_NUM_PARALLEL=1, Flash Attention e cache KV q8_0. São ajustes para equilibrar memória e resposta; alterá-los pode elevar o consumo ou mudar o desempenho. Reinicie o serviço para aplicar as alterações no Compose.

Como reduzir latência

  1. Separe o tempo da primeira carga das gerações seguintes; observe load_duration e eval_duration.
  2. Repita a mesma pergunta e compare tokens, contexto e ollama ps.
  3. Use modelo ou contexto menores quando a memória estiver pressionada ou houver offload para CPU.
  4. Limite saídas com num_predict quando a tarefa não exigir respostas longas.
  5. Evite vários modelos carregados simultaneamente nesta configuração.

Problemas frequentes

  • Connection refused: confira serviço e logs; use localhost no host e ollama dentro da rede Compose.
  • Model not found: confira nome/tag com ollama list e baixe com ollama pull.
  • Lentidão ou falta de memória: tente modelo/contexto menores e observe CPU, GPU e RAM.
  • GPU não utilizada: confira driver, GPU no WSL, Container Toolkit e logs.
  • FROM não acha arquivo: a CLI está no container; copie ou monte pesos em caminho visível nele.
  • Resposta pior após customização: restaure o template original e confira ollama show --modelfile.

Exposição de rede: o Compose limita a API ao loopback. Se mudar o binding, planeje firewall, autenticação por gateway/proxy e controle de acesso antes de permitir conexões de outros computadores.
